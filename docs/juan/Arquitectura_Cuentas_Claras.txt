1. QUÉ ES EL SISTEMA
----------------------------------------------------------------------
Cuentas Claras es una aplicación web de finanzas personales y familiares, en español y en
pesos colombianos (COP, siempre enteros, nunca decimales). Permite:
  - Registrar gastos diarios y administrar categorías (propias y del sistema).
  - Asignar un ícono propio a cada categoría (elegido de un catálogo de 16 opciones).
    Si el usuario o el admin no eligen uno, se usa un fallback automático (por nombre para
    las del sistema, por bloque 50/30/20 para las demás).
  - Registrar gastos fijos mensuales (arriendo, servicios...) con vencimientos y alertas
    automáticas 3 días antes.
  - Simular créditos (sistema francés) y guardar las simulaciones.
  - Ver un informe mensual contra la regla 50/30/20.
  - Metas de ahorro INDIVIDUALES o COMPARTIDAS entre DOS usuarios "familiar" (máx. 2),
    con privacidad de aportes.
  - Cambiar el tipo de cuenta (estándar <-> familiar) desde Ajustes. Exclusivo para
    estandar y familiar; el admin no tiene acceso.
  - Cambiar el correo electrónico con verificación por enlace (token de un solo uso,
    1 hora, correo al NUEVO destino).
  - Administración (usuarios, roles, categorías del sistema, estadísticas agregadas
    y dashboard del administrador en /admin/panel).
  - El admin también puede elegir el ícono de cada categoría del sistema.
  - Auditoría de acciones del admin en /admin/auditoria (solo lectura).
  - Modo claro / oscuro con persistencia en localStorage y favicon dinámico.
  - Tinte por rol: verde (estándar), morado (familiar), azul (administrador).
  - Iconografía por categoría (SVG propio, color por bloque 50/30/20, personalizable).
  - Skip link, página 403 y 404 personalizadas, expiración de sesión (15 min),
    correos con identidad de marca.
  - Seguridad reforzada en J9:
    · CSP (Content-Security-Policy) + X-Frame-Options + nosniff + HSTS.
    · Notificaciones de seguridad por correo (password/email/account/login).
    · Re-autenticación (current_password) para acciones destructivas.
    · Registro de auditoría de cada cambio hecho por el admin.
    · Notificación al usuario cuando sus intentos de login se bloquean.
  - Onboarding tour guiado (7 pasos en dashboard, 6 en admin) con spotlight,
    tooltip que se posiciona arriba/abajo del target, persistencia en
    localStorage, y botón "Ver tour de nuevo" en Ajustes/Perfil.
  - Foto de perfil circular, editable desde Ajustes/Perfil mediante un overlay
    "Cambiar ícono" que abre el selector de archivos.
  - El administrador puede eliminar categorías del sistema SOLO si no tienen
    gastos ni gastos fijos asociados.
  - Almacenamiento de imágenes: dev usa symlink local (storage:link),
    producción puede migrar a S3/R2 sin cambiar el código (el disk 'public' es
    la abstracción).
El diseño visual YA ESTÁ HECHO (vistas Blade + CSS + JS). EL DISEÑO NO SE CAMBIA.

Equipo: Juan (base, seguridad, reglas), Nikol (dinero del día a día), Valeria (cálculo y
análisis). Tareas J1..J9, N1..N5, V1..V5.

4. ROLES (3) Y QUÉ PUEDE HACER CADA UNO
----------------------------------------------------------------------
  estandar ........ gastos (index, create, store, update, destroy, edit),
                    categorías (con ícono elegible), gastos fijos,
                    notificaciones, simulador, informes, panel, ajustes
                    (perfil con ingreso mensual, tipo-cuenta, eliminar cuenta,
                    cambio de correo, FOTO DE PERFIL) y METAS INDIVIDUALES.
                    NO entra a administración.
  familiar ........ todo lo del estándar + metas COMPARTIDAS y puede ACEPTAR
                    invitaciones a metas compartidas.
  administrador ... SOLO administración. En Ajustes, únicamente `perfil`
                    (nombre, correo, contraseña, FOTO DE PERFIL) y
                    `confirmar-correo`.
                    NO tiene ingreso mensual: el campo no se muestra y la regla
                    prohibitedIf lo rechaza si llega por POST.
                    NO puede cambiar tipo de cuenta ni eliminar su cuenta desde
                    Ajustes (solo desde /admin/usuarios si hay otro admin).
                    NUNCA ve montos ni datos financieros de nadie.
                    Recibe 403 en gastos, créditos, metas, informes y panel.
                    Puede elegir el ícono de cada categoría del sistema desde
                    /admin/categorias.
                    Puede ELIMINAR categorías del sistema SOLO si no tienen
                    gastos ni gastos fijos (COUNT = 0). Requiere re-auth.
                    Puede cambiar su FOTO DE PERFIL como cualquier usuario.
                    Accede a /admin/panel (dashboard), /admin/usuarios,
                    /admin/categorias, /admin/estadisticas y /admin/auditoria.
Estado de cuenta: users.activo (booleano).
"rol" y "activo" NO son asignables en masa.
Ocultar un enlace del menú NO protege: middleware + Policies.
Cambio de tipo de cuenta: Ajustes > Tipo de cuenta, vía ServicioCuentas::cambiarTipo.
No cierra la sesión. Regla: estandar -> familiar siempre; familiar -> estandar se
bloquea con metas compartidas activas. Cambio de rol por admin:
ServicioCuentas::cambiarRol.
Cambio de correo: Ajustes > Perfil, requiere contraseña actual y verificación por
enlace al NUEVO correo. Cierra la sesión al confirmar.

Efecto visual del rol:
  Estándar → botones/avatar/ítems activos/logo/favicon en primary (verde).
  Familiar → esos mismos elementos en tertiary (morado).
  Administrador → esos mismos elementos en la familia --admin-* (azul Core Blue).
  El cambio se aplica en el siguiente render. El favicon se regenera vía JS.
  Los correos también respetan el tinte del rol (vía PHP).
  Los iconos de categoría usan colores por BLOQUE 50/30/20, no por rol:
  necesidades (--need, azul), discrecionales (--want, morado), ahorro (--save, verde).

RE-AUTENTICACIÓN:
  El admin debe ingresar su contraseña actual para:
    · Eliminar un usuario (EliminarUsuarioRequest).
    · Activar / desactivar una categoría del sistema
      (EliminarCategoriaSistemaRequest).
    · Eliminar una categoría del sistema (EliminarCategoriaSistemaRequest).
  Motivo: si el admin deja la sesión abierta, un tercero no puede ejecutar
  acciones destructivas sin conocer la contraseña.

11. REGLAS DE NEGOCIO QUE NO SE PUEDEN ROMPER
----------------------------------------------------------------------
Seguridad y privacidad
  - Toda consulta parte del usuario autenticado. Se prueba con dos usuarios.
  - Policy antes de leer, editar o borrar. Contraseñas con hash. CSRF.
  - El administrador nunca toca datos financieros. Ajeno -> 403.
  - Mensajes de error genéricos hacia afuera.
  - Límite de intentos en login y recuperación.
  - Consentimiento de datos obligatorio en el registro, con fecha.
  - Expiración de sesión por inactividad: 15 minutos vía middleware
    'sesion.inactividad'.
  - Cabeceras de seguridad HTTP obligatorias: X-Frame-Options, nosniff,
    Referrer-Policy, Permissions-Policy, CSP, HSTS (producción + HTTPS).
  - Re-autenticación (current_password) obligatoria para: eliminar usuario,
    activar/desactivar categoría del sistema, eliminar categoría del sistema.
  - Auditoría obligatoria en cada cambio de admin: usuario.rol,
    usuario.suspender/reactivar, usuario.eliminar, categoria.crear/actualizar/
    desactivar/reactivar/eliminar.
  - Notificación de seguridad obligatoria en: password.changed,
    email.changed (al correo VIEJO), account.suspended, login.new_ip,
    login.blocked.
Metas
  - Individual: solo creador. Estándar y familiar.
  - Compartida: solo familiar, máx. 2 participantes.
  - Invitar a un estándar: permitido + notificación especial.
  - Aceptar: requiere ser familiar.
  - PRIVACIDAD: detalle muestra total conjunto y aporte PROPIO.
  - Familiar -> estándar bloqueado con metas compartidas activas.
Cambio de tipo de cuenta
  - Ajustes > Tipo de cuenta, vía ServicioCuentas::cambiarTipo.
  - Solo estandar y familiar. Admin recibe 403.
  - NO cierra la sesión. 'rol' no es fillable.
Cambio de rol (por admin)
  - Vía ServicioCuentas::cambiarRol. No cierra la sesión del usuario cambiado.
  - Bloquear si quita admin al último admin activo.
  - Bloquear si baja de familiar a estandar con metas compartidas activas.
Cambio de correo
  - Ajustes > Perfil. Requiere contraseña actual si cambia correo o contraseña.
  - Token SHA-256, 1 hora, correo al NUEVO destino.
  - Correo actual sigue activo hasta confirmar. Al confirmar se cierra la sesión.
  - Correo actual y pendiente deben ser únicos.
Eliminar cuenta / suspender
  - Vía ServicioCuentas. No dejar el sistema sin admin activo.
  - Admin no puede eliminarse a sí mismo desde el panel.
  - Admin tampoco puede eliminar su cuenta desde Ajustes.
  - Vaciar remember_token antes de Auth::logout.
  - Borrar foto de perfil del disco antes del delete.
Restablecer contraseña
  - Enlace de un solo uso, vence en 30 minutos (AUTH_PASSWORD_RESET_EXPIRE).
  - Mensaje neutro. Correo con identidad de marca.
  - Tras reset exitoso, notifica password.changed.
Gastos fijos y alertas
  - Solo mensuales. Si el mes no tiene ese día, último día del mes.
  - Alerta a 3 días y una de vencido. Comando diario IDEMPOTENTE.
  - Vencido cancela por_vencer pendiente y crea vencido.
  - Marcar pagado cancela la alerta pendiente.
  - Cada gasto fijo muestra su icono por categoría (--need/--want/--save).
Simulador de créditos

Informes 50/30/20

Dashboard

Administración

      · Validación: JPG/PNG/WebP, máx 2 MB.
      · Se borra del disco al eliminar la cuenta.
      · NO se guarda la imagen en la BD (solo el path).
      · Motivo: identidad visual del usuario sin dependencia de servicios
        externos en desarrollo, con migración limpia a S3/R2 en producción
        sin cambios de código (ver §17).

17. ALMACENAMIENTO DE IMÁGENES: DESARROLLO Y PRODUCCIÓN
----------------------------------------------------------------------

Contexto
-------
Cuentas Claras guarda imágenes (hoy: avatares de perfil; mañana: adjuntos
de gastos, comprobantes, etc.). La primera funcionalidad que usó esto es
la foto de perfil (decisión #70). El código usa la abstracción de Laravel
`Storage::disk('public')` y `$archivo->store('avatares', 'public')`,
por lo que la ubicación física del archivo la decide
`config/filesystems.php`, NO el controller.

BD vs disco
-----------
  · En la BD SOLO se guarda el path relativo: users.foto_perfil
    = "avatares/abc123.jpg". NUNCA la imagen.
  · El archivo real vive en el disk (dev: storage/app/public/; prod: bucket
    S3/R2).
  · Motivos para no guardar imágenes en la BD:
    - Una imagen de 2 MB en un BLOB hace que cada SELECT del usuario
      cargue 2 MB innecesarios.
    - El dump de la BD crece de MB a GB.
    - El navegador no puede cachear imágenes que vienen dentro de un SELECT.
    - No se puede servir desde CDN.
    - Cada imagen descargada consume una conexión de BD.

DESARROLLO (local)
------------------
  Disk: 'public' → storage/app/public/.
  URL pública: /storage/avatares/abc.jpg.
  Requisito: symlink public/storage → storage/app/public.

  Setup único:
    php artisan storage:link
    # Windows si falla el symlink:
    rmdir public\storage 2>nul
    mklink /J public\storage storage\app\public

  Verificar:
    ls -la public/storage
    # debe ser un symlink a ../storage/app/public

  El accessor User::avatar_url devuelve URL RELATIVA:
    return '/' . 'storage/' . ltrim($this->foto_perfil, '/');
    → /storage/avatares/abc.jpg

  Motivo de la URL relativa:
    - 'self' de la CSP matchea contra el origen de la página.
    - Si el usuario entra por http://localhost:8000 y Storage::url()
      genera http://127.0.0.1:8000/storage/..., el origen es DISTINTO
      y la CSP bloquea la imagen (CSP: img-src 'self' data: https:).
    - Con URL relativa, el navegador la resuelve contra el origen actual,
      sea localhost, 127.0.0.1 o el dominio real en prod.
    - No requiere tocar .env, ni CSP, ni APP_URL.

  Variables de .env relevantes:
    APP_URL=http://127.0.0.1:8000   (o el host que uses en el navegador)
    FILESYSTEM_DISK=local           (el default; el disk 'public' es
                                     explícito en el código)
    FILESYSTEM_URL=                 (vacío; Laravel usa el path del disk)

  Windows + Herd + artisan serve:
    - `php artisan storage:link` a veces crea una copia en vez de symlink.
      Verificar con `dir public\storage` que diga <JUNCTION> o <SYMLINKD>.
    - Si dice <DIR> (carpeta normal), las fotos subidas nuevas NO se van a
      ver: recrear con `mklink /J`.
    - Si aún así da 403/404, la alternativa robusta es mover los archivos
      a public/uploads/ (ver "Fallback" abajo).

PRODUCCIÓN (S3/R2 y equivalentes)
----------------------------------
  Disk: 's3' o 'r2' → bucket del proveedor (S3, Cloudflare R2,
       DigitalOcean Spaces, Backblaze B2, MinIO self-hosted).

  Opciones recomendadas:
    1. Cloudflare R2: no cobra egress (tráfico de salida). Es lo más
       económico para apps con muchas lecturas de imágenes.
    2. Amazon S3: estándar de la industria, integración perfecta con
       Laravel.
    3. DigitalOcean Spaces / Backblaze B2: alternativas más baratas.
    4. MinIO: si la app corre on-premise con servidor propio.

  Ventajas sobre disco local en VPS:
    - Escalable: no te preocupas por el tamaño del disco.
    - Rendimiento: CDN integrado (R2/S3 lo traen).
    - Seguridad: los archivos no se ejecutan en el servidor web.
    - Desacoplamiento: los archivos persisten si el servidor se reemplaza.
    - Multi-servidor: todos los nodos leen el mismo bucket.

  Setup (ejemplo con Cloudflare R2, equivalente para S3):

    1. Crear el bucket en el panel del proveedor (público en lectura).

    2. Instalar el adapter de S3 (compatible con R2):
       php /c/Users/juane/.config/herd-lite/bin/composer.phar require
         league/flysystem-aws-s3-v3 "^3.0"

    3. config/filesystems.php → agregar disk 'r2':
       'r2' => [
           'driver'                  => 's3',
           'key'                     => env('R2_ACCESS_KEY_ID'),
           'secret'                  => env('R2_SECRET_ACCESS_KEY'),
           'region'                  => 'auto',
           'bucket'                  => env('R2_BUCKET'),
           'url'                     => env('R2_URL'),
           'endpoint'                => env('R2_ENDPOINT'),
           'use_path_style_endpoint' => true,
           'throw'                   => true,
       ],

    4. .env en producción:
       R2_ACCESS_KEY_ID=...
       R2_SECRET_ACCESS_KEY=...
       R2_BUCKET=cuentas-claras-avatares
       R2_URL=https://pub-xxxxx.r2.dev
       R2_ENDPOINT=https://xxxxx.r2.cloudflarestorage.com

    5. config/filesystems.php → apuntar el disk 'public' a 's3' o 'r2'.
       Opción A (recomendada): cambiar el contenido del disk 'public' para
       que use driver 's3' con las credenciales del bucket:
         'public' => [
             'driver' => 's3',
             'key'    => env('R2_ACCESS_KEY_ID'),
             // ...
         ],
       Con esto, el código existente (`Storage::disk('public')`) NO cambia.
       Esta es la magia de la abstracción de Laravel.

       Opción B: mantener disk 'public' local y crear disk 'r2', cambiando
       el código a Storage::disk('r2'). NO recomendado (acopla el código
       al proveedor).

    6. El accessor User::avatar_url debe detectar prod y devolver la URL
       COMPLETA del bucket:
         public function getAvatarUrlAttribute(): ?string
         {
             if (!$this->foto_perfil) return null;
             if (!Storage::disk('public')->exists($this->foto_perfil)) return null;
             // En dev: '/storage/avatares/abc.jpg' (relativa)
             // En prod S3: 'https://pub-xxxxx.r2.dev/avatares/abc.jpg'
             return Storage::disk('public')->url($this->foto_perfil);
         }
       Ojo: `Storage::disk('public')->url()` con driver s3 devuelve la URL
       completa automáticamente. Con driver local devuelve '/storage/...'
       si el disk tiene 'url' => env('APP_URL').'/storage' configurado,
       o una URL absoluta con APP_URL si no lo tiene. Por eso en dev
       preferimos URL relativa (ver "Motivo de la URL relativa" arriba).
       Solución unificada: en producción, llamar directamente
       ->url() (que da la URL del bucket); en dev, devolver la relativa
       concatenada manualmente. Se puede resolver con un if
       (app()->environment('local')).

    7. CSP: la cabecera actual (img-src 'self' data: https:) cubre S3/R2
       porque usan HTTPS. NO requiere modificar SecurityHeaders al migrar.
       Si en el futuro se usa un bucket por HTTP (no recomendado), habría
       que añadirlo explícitamente.

    8. Backups: los archivos viven en el bucket, no en el servidor. El
       backup del bucket lo gestiona el proveedor (versionado, reglas de
       ciclo de vida). El backup de la BD sigue siendo el script
       backup-cuentas-claras.sh (o equivalente).

    9. deploy.sh: si se usa S3/R2, NO ejecutar `php artisan storage:link`
       (no aplica). El archivo va directo al bucket.

    10. Migración de archivos existentes (de dev local a prod S3):
        - Opción A: borrar todos los avatares de dev, subir a prod y pedir
          a los usuarios que vuelvan a subir su foto.
        - Opción B: script con `aws s3 sync` o `rclone`:
            aws s3 sync storage/app/public/avatares/ s3://bucket/avatares/
        - Opción C: rclone (compatible con R2):
            rclone sync storage/app/public/avatares/ r2:bucket/avatares/

VPS simple (sin S3/R2)
----------------------
  Si el proyecto se queda en un solo servidor (VPS) y no hay necesidad de
  escalar:

    1. Correr `php artisan storage:link` en el servidor (crea el symlink
       real, Linux lo soporta sin trucos).
    2. Permisos correctos (usuario www-data o el del servidor web):
         sudo chown -R www-data:www-data storage bootstrap/cache
         sudo find storage -type d -exec chmod 775 {} \;
         sudo find storage -type f -exec chmod 664 {} \;
    3. APP_URL=https://cuentasclaras.com (dominio real con HTTPS).
    4. Backups: incluir storage/app/public/ en el backup (además de la BD).
       El script backup-cuentas-claras.sh debe empaquetar
       storage/app/public/avatares/ junto con el dump de la BD.

Fallback (Windows + artisan serve + symlink roto)
-------------------------------------------------
  Si el symlink no funciona en Windows con artisan serve:

    1. Cambiar el `store()` en AjustesController@actualizarPerfil:
       $nombre = uniqid('av_') . '.' . $foto->getClientOriginalExtension();
       $foto->move(public_path('uploads/avatares'), $nombre);
       $usuario->foto_perfil = 'uploads/avatares/' . $nombre;

    2. Cambiar el accessor avatar_url:
       if (!$this->foto_perfil) return null;
       if (!is_file(public_path($this->foto_perfil))) return null;
       return '/' . ltrim($this->foto_perfil, '/');

    3. Cambiar ServicioCuentas::eliminarCuenta:
       if ($usuario->foto_perfil && is_file(public_path($usuario->foto_perfil))) {
           @unlink(public_path($usuario->foto_perfil));
       }

    4. mkdir public/uploads/avatares
    5. Re-subir la foto.

  Desventaja: no es portable a producción con S3. Solo si el proyecto es
  escolar y se queda en Windows local.

CRON DE PRODUCCIÓN (OBLIGATORIO)
------------------------------------------
Para que las tareas programadas (alertas:gastos-fijos, informes:guardar-mensuales,
informes:notificar-disponibles) se ejecuten, el servidor DEBE tener este cron
corriendo cada minuto:

  * * * * * cd /ruta-del-proyecto && php artisan schedule:run >> /dev/null 2>&1

Sin este cron, los comandos nunca se disparan en producción (aunque estén
programados en routes/console.php).

Checklist al migrar a producción con S3/R2:
------------------------------------------
  [ ] Crear bucket + configurar CORS (si aplica) + permisos públicos de
      lectura.
  [ ] composer require league/flysystem-aws-s3-v3.
  [ ] Configurar .env (R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY, R2_BUCKET,
      R2_URL, R2_ENDPOINT).
  [ ] Cambiar config/filesystems.php: disk 'public' con driver 's3'.
  [ ] Ajustar accessor avatar_url para devolver ->url() en producción.
  [ ] Verificar CSP: img-src 'self' data: https: (ya cubre el bucket).
  [ ] Migrar archivos existentes con rclone/aws s3 sync.
  [ ] deploy.sh: NO ejecutar storage:link.
  [ ] Probar: subir foto, ver foto en topbar, eliminar foto, eliminar
      cuenta.
  [ ] Backup del bucket: configurar versionado o lifecycle.
  [ ] Documentar en docs/juan/backups.md.
