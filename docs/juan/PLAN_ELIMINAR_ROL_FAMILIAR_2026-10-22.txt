======================================================================
1. RESUMEN EJECUTIVO
======================================================================

Objetivo: eliminar el rol "familiar" de la aplicación. Todos los usuarios
existentes con rol "familiar" pasan a "estandar". Las metas compartidas
siguen funcionando pero ahora cualquier usuario "estandar" puede crearlas,
invitar y aceptar invitaciones. El rol "administrador" no se toca.

Resultado final:
  · Enum users.rol: estandar | administrador (familiar desaparece del código)
  · Metas compartidas: cualquier estandar puede crear, invitar, aceptar
  · Tipo de cuenta: el usuario ya no elige. Todo el registro es "estandar"
  · Tinte visual: verde (estandar), azul (admin). El morado del "familiar"
    deja de usarse (el CSS queda en theme.css por si se reactiva).
  · El concepto "tipo de cuenta" desaparece de la UI.

Antes (3 roles):                Después (2 roles):
  - estandar                      - estandar (todas las funciones)
  - familiar                      - administrador (solo admin)
  - administrador

Tests:
  · Antes: 209 passing
  · Después: ~195 passing (15-20 tests reescritos/eliminados)


======================================================================
2. MOTIVACIÓN Y ADVERTENCIAS
======================================================================

Por qué hacerlo:
  · El rol "familiar" solo agrega 2 capacidades (crear metas compartidas,
    aceptar invitaciones). Todo lo demás es idéntico al estandar.
  · El usuario tiene que ir a Ajustes a cambiar de tipo para hacer algo
    que ya debería poder hacer.
  · Es fricción UX que no aporta valor de negocio (el producto no cobra
    diferente por eso).

ADVERTENCIAS:
  · Esta es una decisión de producto, no de código. Debe ser aprobada
    por el equipo (Juan + Nikol + Valeria).
  · Es un one-way door. Reactivar "familiar" después implica reescribir
    todo lo que se borre aquí.
  · Contradice las decisiones documentadas #7, #18, #24 y el cierre del
    J5 del 2026-10-08.
  · Afecta la landing y el registro (N5, Nikol).
  · Si algún usuario tiene una meta compartida activa al momento de la
    migración, sigue funcionando, pero pierde la separación de roles.

Alternativa recomendada (si no estás seguro): la Opción B documentada en
el chat del 2026-10-22. El sistema auto-sube a "familiar" cuando el
usuario quiere compartir una meta, sin que lo vea. Son 1-2 horas y no
requiere migración. Esta Opción A es solo si quieres eliminar el rol
por completo del código.

5. MIGRACIÓN DE BASE DE DATOS
======================================================================

Archivo: database/migrations/2026_10_22_000003_eliminar_rol_familiar.php

<?php

use Illuminate\Database\Migrations\Migration;
use Illuminate\Support\Facades\DB;

/**
 * Elimina el rol "familiar": todos los usuarios que lo tenían pasan a
 * "estandar". No se borra ningún dato de metas ni participaciones; las
 * metas compartidas activas siguen funcionando.
 *
 * La columna users.rol NO se altera a nivel de esquema (SQLite no permite
 * cambiar el CHECK fácilmente). La validación del valor permitido se hace
 * a nivel de aplicación (RegistroController, ServicioCuentas).
 *
 * Reversible: down() vuelve a poner 'familiar' a quien se llamaba
 * "estandar" y tenga metas compartidas activas. Es una aproximación
 * (no todos los estandar eran familiar antes), pero permite revertir
 * sin perder funcionalidad.
 */
return new class extends Migration
{
    public function up(): void
    {
        // 1. Registrar en auditoría a los usuarios afectados.
        $afectados = DB::table('users')->where('rol', 'familiar')->count();

        DB::table('users')->where('rol', 'familiar')->update(['rol' => 'estandar']);

        if ($afectados > 0) {
            \Illuminate\Support\Facades\Log::info(
                "Migración eliminar_rol_familiar: {$afectados} usuarios pasaron de familiar a estandar."
            );
        }
    }

    public function down(): void
    {
        // Aproximación: usuarios estandar con metas compartidas activas
        // vuelven a ser familiar. Es la mejor reconstrucción posible sin
        // un backup previo.
        $ids = DB::table('participaciones_meta')
            ->where('estado_invitacion', 'aceptada')
            ->pluck('user_id')
            ->merge(
                DB::table('metas')
                    ->where('compartida', true)
                    ->where('estado', 'activa')
                    ->pluck('creador_id')
            )
            ->unique()
            ->values();

        if ($ids->isNotEmpty()) {
            DB::table('users')
                ->whereIn('id', $ids)
                ->where('rol', 'estandar')
                ->update(['rol' => 'familiar']);
        }
    }
};


Ejecutar:
  php artisan migrate

Verificar:
  sqlite3 database/database.sqlite "SELECT rol, COUNT(*) FROM users GROUP BY rol;"
  O con tinker:
  php artisan tinker --execute="echo App\Models\User::selectRaw('rol, count(*) as n')->groupBy('rol')->get();"

Debe devolver solo 'estandar' y 'administrador'.

6.4 LA COLUMNA users.rol NO SE ALTERA
---------------------------------------
  En SQLite, el esquema no tiene CHECK constraint sobre rol. En MySQL de
  producción (cuando se migre), si se puso ENUM('estandar','familiar',
  'administrador'), se puede:
    a) Dejar el ENUM con los 3 valores y validar en app (recomendado).
    b) ALTER TABLE users MODIFY rol ENUM('estandar','administrador');
       (requiere migración de esquema nueva).
  Recomendación: opción (a). La app nunca asigna 'familiar'.
